    Understand the whole project, one step at a time

    This guide walks through the rate-limited banking API one step at a time: the problem, the four algorithms, how a request moves through the code, the safety features, and what went wrong when it went live. Every step names the decision, why it was made, what it costs, and where it lives in the code. Tick a step off once you could explain it without notes.

    STEP 01

    The big picture

    Ledgerline is a pretend bank with a public API. Developers sign up, get an API key, and call endpoints to read balances, move money and pay people. The interesting part is everything that stops those calls from overwhelming or abusing the bank.

    flowchart LR
  U["Developer / dashboard"] --> V["FastAPI app on Vercel
    (many serverless instances)"]
  V -- "rate limit decisions" --> R[("Redis
    Upstash")]
  V -- "customers, keys, ledger,
    idempotency, usage" --> P[("Postgres
    Neon")]

    Three ideas carry the whole project:

    • Four rate limiting algorithms, each used where it fits a real banking problem.
    • The Strategy pattern, so every algorithm is interchangeable behind one interface.
    • Serverless-safe state: anything shared between requests lives in Postgres or Redis, never in one server's memory.

    Live: rate-limit-project.vercel.app · Code: github.com/udaydaroch/rateLimitProject

    Check yourself: describe the project in two sentences.

    "It's a sandbox banking API where developers get keys and move fake money. I used it to show how four rate limiting algorithms solve different problems: burst control, fraud limits, payment smoothing and billing quotas. It runs on serverless infrastructure with Postgres and Redis."

    STEP 02

    What rate limiting is, and why a bank needs it

    Rate limiting means deciding, for each incoming request, "is this caller allowed to do this right now?" When the answer is no, the API returns 429 Too Many Requests with a Retry-After header saying how many seconds to wait.

    A bank needs it for different reasons in different places:

    RiskWhat could go wrongLimit that handles it
    OverloadOne buggy client hammers the API and slows it for everyone.Token bucket per API key
    FraudA stolen account is drained with many quick transfers.Sliding window per account
    Downstream limitsThe payment network between banks rejects spikes.Leaky bucket per customer
    Business rulesPlans are sold as "1,000 calls a day".Fixed window per customer
    Brute forceSomeone guesses API keys over and over.Fixed window per IP
    Decision

    Use a different algorithm for each job instead of one global limit. This is the core idea of the project: no single algorithm is best, each makes a different trade-off.

    Every limit is keyed: it counts per something (per API key, per account, per IP). The key decides who shares a limit. Transfers are keyed per account because the fraud risk is about money leaving one account, regardless of which API key sends it.

    Check yourself: why is the transfer limit keyed by account and not by API key?

    Because the thing being protected is the money in the account. A customer could have several API keys; if the limit were per key, an attacker with two keys could double the drain rate.

    STEP 04

    Algorithm 1: token bucket (everyday requests)

    Each API key has a cup holding up to 10 tokens (free plan). Each request spends one token. Tokens drip back at 2 per second. An empty cup means 429.

    It stores only two numbers per key: tokens and last_refill_time. There's no background timer; on each request it works out how many tokens have dripped in since last time:

    tokens = min(capacity, tokens + (now - last) * refill_rate)   # catch up
if tokens >= 1:
    tokens -= 1                                                # allowed
else:
    retry_after = (1 - tokens) / refill_rate                   # time until 1 token exists
    t = 0.0 sApp opens, fires 10 calls at once. Tokens 10 → 0. All 200
    t = 0.0 s11th call: no tokens. 429, retry after 1 ÷ 2 = 0.5 s
    t = 0.5 sOne token has dripped in. Call succeeds. 200
    t = 5.5 sQuiet for 5 s: cup full again (capped at 10).
    Decision

    Use it for general API traffic because real apps are bursty: many calls on launch, then nothing. It allows the burst but caps the long-run average.

    Trade-off

    It doesn't smooth traffic: a full burst of 10 hits the server at once. That's fine for protecting our own API, but wrong for a slow system downstream (see the leaky bucket in step 07).

    Where: app/ratelimit/token_bucket.py

    Check yourself: why does a blocked call say RateLimit-Reset: 5?

    Reset is the time until the bucket is completely full. An empty bucket of 10 refilling at 2/s needs 10 ÷ 2 = 5 s.

    STEP 05

    Algorithm 2: sliding window log (transfer fraud limit)

    At most 5 transfers out of one account in any 60 seconds. "Any 60 seconds" means the 60 seconds ending right now, so the window slides with the clock.

    It keeps the timestamp of every accepted transfer. On a new transfer it throws away timestamps older than 60 s, then counts what's left:

    while log and log[0] <= now - 60:
    log.popleft()                       # slid out of the window
if len(log) < 5:
    log.append(now)                     # allowed
else:
    retry_after = log[0] + 60 - now     # when the oldest one expires

    Why not a simpler fixed window?

    A fixed window resets at each minute boundary. An attacker could send 5 transfers at 12:00:59 and 5 more at 12:01:00, which makes 10 in one second, all allowed. The sliding window has no boundary to exploit. Both behaviours are proven by tests: test_fixed_window_allows_boundary_burst and test_sliding_window_blocks_boundary_burst.

    Decision

    Use the exact (log) version because this is a security control. Exactness matters more than memory here.

    Trade-off

    Memory grows with the limit: it stores up to 5 timestamps per account. For a limit like 10,000/hour you'd use a sliding window counter instead, which approximates this with two fixed-window counts and O(1) memory.

    Where: app/ratelimit/sliding_window.py

    Check yourself: 5 transfers at :10 :20 :30 :40 :50. When can the 6th go through?

    At 12:01:10 or later, when the 12:00:10 entry is more than 60 seconds old and slides out.

    STEP 06

    Algorithm 3: fixed window (quotas, lockouts, signups)

    Time is cut into aligned blocks (each UTC day, each minute, each hour) with one counter per block. When the block changes, the count starts again at zero.

    window_id = int(now // window_length)      # e.g. "day number since 1970"
if stored_window_id != window_id:
    count = 0                              # new window
if count < limit:
    count += 1                             # allowed

    It's used in three places:

    • Daily quota: free plan 1,000 calls/day, reset at midnight UTC. Pro plan 50,000/day, and going over is billed (overage) instead of blocked.
    • Auth lockout: 20 wrong API keys from one IP in a minute locks that IP until the minute ends.
    • Signups: 10 new test customers per IP per hour on the public site.
    Decision

    Quotas are a contract and billing idea. Customers need a predictable reset ("every day at midnight UTC") they can see on an invoice. A rolling 24 hours would be impossible to explain on a bill.

    Trade-off

    The boundary loophole from step 05 exists here too (up to 2× the limit around midnight). For a daily quota or a lockout that doesn't matter, and it's the cheapest algorithm: one integer per key.

    Where: app/ratelimit/fixed_window.py · overage logic in app/deps.py (metered_client)

    Check yourself: same algorithm, but free plan blocks and pro plan doesn't. How?

    The limiter only reports "over the limit". What happens next is a business decision in metered_client: free plans raise a 429, pro plans serve the request, add an X-Quota-Overage: true header, and bill it at the overage rate.

    STEP 07

    Algorithm 4: leaky bucket (payroll payouts)

    Payouts pour into a bucket that holds 20 and drains at a constant 1 per second. If a new payout would overflow it, that payout is rejected. Because the drain is constant, each payout's position tells you exactly when it will be sent.

    level = max(0, level - (now - last) * leak_rate)   # drain since last time
if level + 1 <= capacity:
    delay = level / leak_rate                       # everyone ahead of me goes first
    level += 1                                      # accepted, sent at now + delay
else:
    retry_after = (level + 1 - capacity) / leak_rate

    Submitting payroll for 22 people at once: payouts 1–20 are accepted with delays 0, 1, 2 … 19 seconds, and 21–22 are rejected as queue_full.

    Token bucket vs leaky bucket

    Both use a "bucket", but they do opposite jobs. A token bucket lets bursts through to the server, as long as the average stays under the limit. A leaky bucket absorbs bursts and sends work on at a fixed pace, so whatever is downstream never sees a spike. Use the first to protect yourself, the second to protect someone slower than you.

    Decision

    Payment networks between banks accept a steady rate and penalise spikes, so payouts are shaped, not just capped. The batch endpoint costs one API token for the whole batch, but each payout passes the leaky bucket individually.

    Honest limitation

    There's no real payment network. A payout's status flips from queued to dispatched once its dispatch_at time passes. A real system would have a background worker sending them.

    Where: app/ratelimit/leaky_bucket.py · create_payout_batch in app/main.py

    Check yourself: why does a payroll batch have a per-item result instead of failing as a whole?

    So the 20 that fit go out on time and the client can resubmit just the rejected ones later. Rejecting the whole batch because two didn't fit would delay everyone's pay.

    STEP 08

    The Strategy pattern holding it together

    Every algorithm is a strategy with the same interface, and the app only ever talks to a context object. Endpoints never know which algorithm is behind a limit.

    RoleClassJob
    Strategy interfaceRateLimitStrategyDefines acquire, peek, reset, describe.
    Concrete strategiesTokenBucket, SlidingWindowLog, FixedWindow, LeakyBucket (+ Redis versions)Each implements only its own maths in _evaluate.
    ContextRateLimiterHolds a strategy, names its keys, can swap strategy with set_strategy().
    Factorycreate_strategy()Builds a strategy from config: ("sliding_window", {"limit": 5, "window": 60}).

    A detail worth mentioning: acquire and peek share one method

    The base class implements acquire() (use it up) and peek() (just look) once. Both take the lock and call the abstract _evaluate(key, cost, consume), with consume true or false. Each algorithm writes its maths once and gets both for free. This is the template method pattern inside the strategy pattern.

    peek() powers GET /v1/limits, which shows the live state of every limiter without using anything up. It's what the dashboard's live meters poll every second.

    Decision

    Policies are data, not code. Changing which algorithm protects something is a one-line edit in policies.py. The payoff showed up later: moving every limiter to Redis needed new strategy classes and a factory option, and no endpoint code changed at all.

    Where: app/ratelimit/ (base.py, limiter.py, factory.py)

    Check yourself: what would you change to give the free plan a 20-token burst?

    Only the Plan entry in policies.py (burst=20). The factory builds the bucket from it; nothing else needs to know.

    STEP 09

    The life of one request

    Follow a transfer request through the code. The order of the checks is itself a set of decisions.

    flowchart TD
  A[Request arrives] --> B{"IP locked out?
    (fixed window)"}
  B -- yes --> X1[429]
  B -- no --> C{"API key valid?"}
  C -- no --> X2["401 + count a failure for this IP"]
  C -- yes --> D{"Token left?
    (token bucket)"}
  D -- no --> X3[429]
  D -- yes --> E{"Daily quota left?
    (fixed window)"}
  E -- "no, free plan" --> X4[429]
  E -- yes --> F{"Idempotency key
    seen before?"}
  F -- "yes, finished" --> R["Replay stored answer"]
  F -- new --> G["Validate accounts"]
  G --> H{"Transfer limit?
    (sliding window)"}
  H -- no --> X5[429]
  H -- yes --> I["Move money + save answer
    (one transaction)"]
  I --> J["Middleware: add headers,
    record usage"]
    1. Auth (authenticate): checks the IP lockout first, then the key. Wrong keys count against the IP.
    2. General limits (metered_client): token bucket per key, then daily quota per customer.
    3. Idempotency check before anything else, so a retry gets the stored answer and doesn't count against the transfer limit again.
    4. Validation before the fraud limit, so a typo in an account number doesn't use up one of your 5 transfers.
    5. The money moves inside a database transaction.
    6. Middleware runs around everything: it adds the RateLimit-* headers and writes one usage record, including for 429s.

    Every response carries headers so a client knows where it stands:

    RateLimit-Policy: token_bucket      # which limit is closest to blocking you
RateLimit-Limit: 10
RateLimit-Remaining: 9
RateLimit-Reset: 1                  # seconds until fully replenished
Retry-After: 1                      # only on 429

    Where: app/deps.py · app/middleware.py

    Check yourself: why is the middleware a raw ASGI middleware instead of a normal FastAPI one?

    It has to see the final status code, including 429s raised inside dependencies, and change response headers as they're sent. Wrapping the ASGI send function gives exactly that, and it reads the decisions the limiters left on request.state.

    STEP 10

    API keys: generated once, stored only as a hash

    A key looks like bk_live_RKcNm7pO_bTfDdWR7dcj7Qqj7cc6gkfMqef0zz2QX: a public 8-character prefix and a 32-character secret.

    • The database stores the prefix (to find the row quickly) and HMAC-SHA256(pepper, secret). Never the secret.
    • The full key is shown once, at signup. If it's lost, you make a new one.
    • Checking a key uses a constant-time comparison, so response timing can't reveal how close a guess was.
    • The pepper is a secret kept in an environment variable, not the database, so a leaked database dump alone can't be used to test guesses.
    Decision: why not bcrypt like passwords?

    Passwords are short and guessable, so they need a deliberately slow hash. API keys are 32 random characters (about 190 bits), which can't be brute-forced however fast the hash is. A fast keyed hash keeps every request's auth check cheap.

    Where: app/security.py

    Check yourself: why have a prefix at all?

    Without it you'd have to hash the incoming secret and compare it against every key. The prefix is an indexed lookup that finds the one row to check, and it's safe to show in the dashboard (bk_live_RKcNm7pO_…) so people can tell keys apart.

    STEP 11

    Idempotency keys: retries never pay twice

    A phone sends a transfer, the connection drops before the answer arrives, and the app retries. Did the first one go through? Without protection, the retry could move the money a second time.

    Money-moving endpoints require an Idempotency-Key header (any unique string, usually a UUID). The bank remembers each key:

    SituationResponse
    New keyRun the transfer, store the answer under the key
    Same key, same body, finishedreplay the stored answer, header Idempotent-Replayed: true
    Same key, first request still running409 request in progress
    Same key, different body422 the client has a bug
    First attempt was rate limited (429) or crashed (5xx)Key is released, so the client can retry with the same key
    Decision: one transaction

    The money movement and the stored answer are saved in the same database transaction. Either both happen or neither does, so a crash can never leave "money moved, but key not marked done".

    Two clean-up rules: keys expire after 24 hours, and an "in progress" marker older than 60 seconds is assumed to belong to a crashed request and can be taken over.

    Where: app/idempotency.py

    Check yourself: why is a 429 not stored as the key's final answer?

    Being rate limited isn't a real outcome of the transfer; it just means "not now". If it were stored, every retry with that key would replay the 429 forever and the transfer could never happen.

    STEP 12

    Keeping the money correct

    • Integer cents everywhere. 2500 means $25.00. Floating point can't represent 0.10 exactly, which is unacceptable for money.
    • A database rule: CHECK (balance_cents >= 0). Even buggy code can't make a balance negative.
    • An atomic debit. The check and the subtraction are one statement:
    UPDATE accounts
   SET balance_cents = balance_cents - :amount
 WHERE id = :account AND balance_cents >= :amount
-- 0 rows changed  →  insufficient funds
    The bug this prevents

    The naive version reads the balance, checks it in Python, then writes. Two transfers arriving at the same moment both read $100, both pass a $80 check, and the account is overdrawn. In one statement, the database handles the two updates one after the other, so the second one sees $20 and fails.

    Where: _debit in app/main.py

    Check yourself: what is a race condition, in one sentence?

    A bug where the result depends on the exact timing of two things happening at once, such as two requests reading the same value before either writes.

    STEP 13

    Cursor pagination for transaction history

    Transaction lists come back 20 at a time with a next_cursor. The next request passes it back to get the following page.

    The cursor is an opaque, base64-encoded "last id you saw". The query is WHERE id < :cursor ORDER BY id DESC LIMIT 21. Asking for one extra row is how the API knows whether has_more is true.

    Decision: why not ?page=3?

    A ledger is written to constantly. With page numbers, each new transaction shifts every page by one, so clients skip or see rows twice. Offsets also get slower the deeper you go (OFFSET 40000 scans 40,000 rows). A cursor is stable and uses the index, so page 1,000 is as fast as page 1.

    Where: app/pagination.py

    Check yourself: why make the cursor opaque instead of just ?after_id=59?

    It keeps the format private, so the server can later change what's inside (say, sort by date plus id) without breaking clients.

    STEP 14

    Usage metering and billing

    Every authenticated call writes one row to usage_events: which key, which endpoint, the status code, whether it's billable, and the UTC day.

    • Billable means status below 400. Blocked (429) calls are recorded so you can see them, but never charged.
    • GET /v1/usage turns the rows into: calls today, calls per day, calls per endpoint, and a bill estimate.
    • Pro plan pricing: $0.40 per 1,000 calls within the quota, $0.80 per 1,000 over it.
    A bug found while testing

    At first, the dashboard's own /v1/usage call also went through the token bucket. After the burst demo emptied the bucket, the dashboard couldn't even load your usage to show you why. Fix: management endpoints (/v1/usage, /v1/keys, /v1/limits) need a valid key but aren't rate limited or billed, just as a provider's own dashboard doesn't use up your API limits.

    Where: app/metering.py · management_client in app/deps.py

    Check yourself: why store the UTC day as its own column?

    Grouping by day is then plain SQL that works the same on SQLite and Postgres, with no database-specific date functions.

    STEP 15

    Going live: the bugs that only appeared in production

    Everything passed locally; production found three real problems.

    Bug 1: every page returned 404

    The config had an old-style rule rewriting every path to /api/index. Vercel now detects FastAPI itself, so the app received /api/index for every request. The clue was that the 404 body was FastAPI's own {"detail": "Not Found"}, so the app was running but seeing the wrong path. Fix: delete the rewrite.

    Bug 2: random 401s for valid keys

    The first version kept the database in each server's /tmp folder and the limiters in memory. Vercel runs many short-lived instances. In a live test, requests 1–9 worked and request 10 got 401: it had landed on a second instance where the key didn't exist. Rate limits were also per instance, so they weren't really enforced.

    Fix: move shared state out of the server

    Customers, keys and the ledger moved to Postgres; limiter state moved to Redis. Thanks to the Strategy pattern, Redis meant four new strategy classes and a factory option; no endpoint changed.

    Why Redis needs Lua scripts

    With many instances, two can read "1 token left" at the same moment and both spend it. Each Redis strategy sends its whole read-decide-write as one Lua script, which Redis runs as a single uninterruptible step:

    local tokens = tonumber(redis.call('HGET', key, 'tokens')) or capacity
tokens = math.min(capacity, tokens + elapsed * rate)
local allowed = tokens >= 1
if allowed then tokens = tokens - 1 end
redis.call('HSET', key, 'tokens', tostring(tokens), 'ts', tostring(now))
redis.call('PEXPIRE', key, ttl)          -- idle keys delete themselves

    Details: numbers come back as strings because Redis would cut decimals off Lua numbers; every key has an expiry so unused ones clean themselves up; max(0, now - last) guards against small clock differences between servers.

    Bug 3: locked out of signing up

    The dashboard pre-filled one email per page load. Each extra click on "Sign up" got a 409 "email taken", but each attempt still used one of the 10 signups allowed per IP per hour. Fix: check for an existing email before taking a signup slot, and give the form a fresh email after each signup.

    Other serverless details

    • Real client IP: behind Vercel's proxy every request appears to come from the proxy, so per-IP limits read X-Forwarded-For, trusted only when running on Vercel so nobody can fake their IP locally.
    • Connection pool: each instance keeps up to 4 Postgres connections, with prepared statements turned off as Neon's PgBouncer requires.
    • Schema setup runs on first use behind a Postgres advisory lock, so two cold-starting instances don't race on CREATE TABLE.

    Where: app/ratelimit/redis_strategies.py · app/db.py

    Check yourself: why didn't the 401 bug show up in local testing?

    Locally there's only ever one process, so memory and the SQLite file are always shared. The bug only exists when requests are spread across several separate instances, which is the normal situation on serverless hosting.

    STEP 16

    How it's tested

    • A fake clock. Every strategy takes a clock function. Tests pass one they control and call clock.advance(1.5), so time-based behaviour is tested exactly and instantly, with no sleep().
    • Both backends, same tests. Every algorithm test runs twice: in-memory and Redis (using fakeredis, which can run Lua). The whole API suite also runs twice. That guarantees the two implementations can't drift apart.
    • A cross-instance test: two strategy objects on one Redis share a bucket of 3, and the 4th request between them is blocked.
    • Real Postgres option: TEST_DATABASE_URL=… pytest runs the API tests against Postgres, each in a throwaway schema.
    • Live checks after each deploy: signup, 40 simultaneous requests (zero 401s), each algorithm, idempotency, pagination and usage.

    67 tests, about 2 seconds locally.

    A lesson about test results

    Running the API tests against the real database from New Zealand gave 4 failures, but they were false alarms. Each request took about a second to reach Washington, so the token bucket refilled between requests and the expected 429s never came. Time-based tests depend on fast requests; the same checks passed from inside Vercel's region.

    Where: tests/

    Check yourself: why inject a clock instead of calling time.time() directly?

    So tests control time. Otherwise testing "refills after 60 seconds" would mean really waiting 60 seconds, and results would vary with machine speed.

    STEP 17

    Known limitations and next steps

    Limitations

    • If Redis is down, requests fail with a 500. A real system must choose: fail open (allow everything) for reads, fail closed (block) for money movement.
    • Payouts aren't really sent; there's no background worker or payment network.
    • One database write per request for metering. At scale you'd batch them or send them to a queue.
    • Per-IP limits hit shared networks: an office or university behind one IP shares the 10 signups an hour.
    • The sliding window log uses memory per request; a high limit would need the counter variant.

    Next steps

    • Decide fail-open or fail-closed per endpoint for when Redis is unavailable.
    • Add a real background worker that sends queued payouts.
    • Batch the usage writes instead of one database write per request.
    • Design for multiple instances from the start next time.
